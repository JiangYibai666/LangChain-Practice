## 成本问题
- LLM按**token计费**
- 使用越多，成本越高
- 需要对使用量进行严格限制以控制费用

## 使用限制措施
| 限制内容       | 说明                           |
| -------------- | ------------------------------ |
| 用户消息限制   | 例如每天限制10条或50条消息     |
| 使用权限限制   | 对客户端用户的使用进行限制     |
| 保障措施       | 设置**guardrails**和使用上限   |

> “不能无限制开放使用，否则账单无法控制。”  
> “AWS和LLM服务商都希望用户多用，但我们必须限制以控制成本。”

---

**总结**：架构设计需结合具体使用场景，重点关注成本控制，通过限制用户使用频率和设置保障措施，避免因无限制使用导致高额账单。

## 向量数据库的特点
### 详细说明
- 向量数据库是一个**动态变化的数据库**，具有“有机”特性
- 数据库内容会**每天、每周、甚至每小时更新**
- 需要有**专门的应用程序**负责维护和更新向量数据库
- 需要**调度器（scheduler）或定时任务（cron）**来定期更新向量数据

> 向量数据库是一个“活的有机数据库”，需要根据需求不断更新向量。

## AI与应用架构
### 详细说明
- AI系统将基于向量数据库进行工作
- 应用架构包含**前端数据库**和**前端界面**
- 前端界面可能会包含**复选框（checkbox）**等交互元素
- 应用程序负责与向量数据库和AI模块的交互

| 组件         | 作用                         |
|--------------|------------------------------|
| 向量数据库   | 存储和更新向量数据           |
| AI模块       | 基于向量数据库进行智能处理   |
| 调度器/定时任务 | 定期更新向量数据库           |
| 前端数据库   | 支持前端应用的数据需求       |
| 前端界面     | 用户交互，显示数据和控件     |

# 📚 RAC（检索增强生成）概述

## RAC的定义  
- **RAC** 是指 *检索增强生成（Retrieval-Augmented Generation）*  
- 通过结合 **现有数据库中的文件和业务数据** 与 **大型语言模型（LLMs）固有知识**，实现更有效的信息检索和生成  

## RAC的工作原理  
| 步骤       | 说明                                                         |
|------------|--------------------------------------------------------------|
| 数据来源   | 从公司现有数据库中提取文件和业务数据                           |
| 知识结合   | 将提取的数据与LLMs的固有知识结合                              |
| 信息检索   | 通过向量嵌入（vector embeddings）和数据分块（chunks）进行检索 |
| 生成输出   | 利用增强后的数据生成更符合公司需求的内容                      |

> **总结**：RAC通过“增强”LLMs的固有知识，使其能够更好地服务于公司具体应用场景。

# ⚙️ RAC在系统中的应用

## 现有系统设计  
- 系统中绘制的所有流程和结构均针对RAC设计  
- 向量嵌入和数据分块等技术均用于支持RAC的检索功能  

## RAC的价值  
- 使LLMs不仅依赖自身训练数据，还能结合公司特定数据  
- 提升生成内容的相关性和准确性  
- 促进公司业务数据的智能化利用  

> **重点**：所有设计和实现均围绕RAC展开，确保系统能够有效利用公司数据增强LLMs的能力。
