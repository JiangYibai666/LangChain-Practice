# 🗂️ 数据库表结构设计

### 说明
- **表名**：users
- **字段示例**：
  - 名称（name）
  - 邮箱（email）
- **用途**：存储用户的基本信息

## 实体与公司表设计

### 实体表（entities表）
- **定义**：*用于存储实体的基本注册信息*
- **字段**：
  | 字段名           | 说明                     |
  |------------------|--------------------------|
  | entity registration number | 实体注册号               |
  | UUID             | 唯一标识符               |

  - 不包含其他详细数据

### 公司表（companies表）
- **定义**：*存储实体的详细公司信息*
- **用途**：
  - 保存除实体表以外的所有剩余数据
  - 与实体表配合使用，完成单个实体的完整数据存储

### 关系说明
- **单个实体的上架流程**：
  - 需要同时向两个表插入数据：entities表和companies表
  - entities表负责基础注册信息
  - companies表负责详细公司信息

> “在onboarding任何公司时，我们会有两个不同的表，一个是entities表，另一个是companies表。entities表只存储少量关键信息，其他数据都存储在companies表中。”

# 💡 关键点总结
- users表存储用户基本信息
- 实体信息分为两张表存储：entities表（基础信息）和companies表（详细信息）
- 单个实体的完整数据需要同时写入两个表

# 🛡️ 用户角色与权限管理

## 用户与权限的存储

### 用户信息存储
- 创建用户时，用户信息会保存到 **users 表** 中。
- 给用户分配的权限会保存到 **user privileges 表** 中。
- 可以通过 **user UUID** 来查询对应用户的权限信息。

### 权限详情查询
- 通过 **feature ID** 可以查询对应的功能权限。
- 在 **user privileges action** 中，可以查看该用户对某个功能的具体权限，如：
  - **read**（读取）
  - **write**（写入）
  - **approve**（审批）

## 功能与角色对应关系

### 角色与功能权限
- 角色示例：**RBAC role** 和 **CP user**
- 这两个角色拥有特定的权限集合。

### 功能表查询
- 通过 **feature ID** 可以在 **features 表** 中查询对应的功能详情。
- 该表用于明确功能代码对应的具体功能内容。

| 表名               | 作用                         | 关键字段             |
|--------------------|------------------------------|----------------------|
| users              | 存储用户基本信息             | user UUID            |
| user privileges    | 存储用户权限信息             | user UUID, feature ID|
| user privileges action | 存储用户对功能的具体操作权限 | read, write, approve |
| features           | 存储功能信息                 | feature ID           |

> **总结**：通过用户表和权限表的联合查询，可以明确某个用户在某个功能上的具体权限；通过功能表可以了解功能代码对应的功能内容。
